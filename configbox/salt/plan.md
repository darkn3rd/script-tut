# Salt implementation (static + roster) with a vendored formula

## Context

This repo already has parallel implementations of the same tutorial "lessons"
provisioning area in Chef, Ansible, and Puppet, each living under its own
`configbox/<tool>/` directory and driven off the same shared source of truth
(`scriptbox/config/ubuntu2204.yml`) via a per-tool Ruby generator in
`scriptbox/scripts/`. Salt is next. The user has already created an empty
skeleton (`configbox/salt/{static,roster}/{roots/salt,roots/pillar}/top.sls`
and matching `systems/ubuntu22/Vagrantfile`s) reflecting their intent: two
delivery mechanisms for the same data, mirroring how Puppet has three
classifier styles (site/hiera/enc) that all consume the same generated step
data differently. They also want at least one vendored external module
demonstrated (Salt calls these "formulas"), matching the `.forge-vendor`
pattern already established for Puppet.

Hard requirement carried over from the Puppet work: no comments/docs in the
Salt tree may reference Puppet, Chef, Ansible, or any other CM tool by name -
everything must read standalone, in Salt's own vocabulary.

Key decisions already made this session (do not re-litigate):
- `static/` = masterless `salt-call --local` - a real salt-minion installed
  on the guest, applying against local `file_roots`/`pillar_roots`, data
  delivered the ordinary way (external YAML, looked up automatically).
- `roster/` = `salt-ssh` - agentless, no persistent minion daemon at all -
  driven by a roster file that's regenerated by our own generator and embeds
  the full step-data payload directly as `minion_opts.grains` (mirrors how
  Puppet's "site" classifier inlines everything into one generated file,
  vs. hiera/enc looking data up externally).
- `salt-ssh` needs a working Python + SSH client "control" machine, and this
  dev box's Windows/msys2 host is not a reliable one for that (same root
  problem this repo already hit and solved for Ansible - see
  `configbox/ansible/systems/README.md`'s own "Why not Windows" section,
  which resolved it via `ansible_local`: run the tool *inside* the Linux
  guest, targeting itself, instead of trying to make Windows the control
  node). **Resolution: `salt-ssh` runs inside the Ubuntu guest, targeting
  `127.0.0.1` over a locally-generated SSH keypair** - not from the Windows
  host, not via WSL2. The roster's data payload is still generated on the
  host by Ruby beforehand (that part already works fine cross-platform, same
  as `generate_puppet.rb`), synced into the guest via the existing
  repo-wide `/var/script-tut` share, and only the actual `salt-ssh` command
  itself runs inside the guest via a plain Vagrant shell provisioner.
- External formula: `saltstack-formulas/golang-formula` (confirmed not
  archived, standard formula layout - `golang/init.sls`, `pillar.example`,
  `map.jinja`). Fills a real existing gap: our own `golang-go` step is
  currently a raw `apt` + PPA step with no vendored alternative anywhere
  yet, so swapping in a real formula for the same language is a clean,
  motivated demonstration.

## Approach

### 1. Shared, delivery-agnostic state tree - `configbox/salt/shared_states/lessons/`

Mirrors `shared_modules/lessons` in spirit (one tree, works no matter how
data reaches it), using Jinja instead of Puppet's automatic parameter
binding:

- `map.jinja` - the one lookup every other file uses:
  `{%- set lessons = salt['grains.get']('lessons', {}) or salt['pillar.get']('lessons', {}) %}`,
  with `setdefault` calls for `user`, `common_steps`, `gates` (the four area
  on/off booleans), `areas` (the four areas' own step lists). `static/`
  supplies this via real pillar data; `roster/` supplies it via grains
  embedded in the generated roster file - the tree itself never knows or
  cares which.
- `install_step.jinja` - a Jinja **macro** `install_step(title, step, user,
  home)`, the direct analogue of `install_step.pp`'s `case $type` block, one
  `{% if/elif %}` branch per step type, returning real Salt state IDs
  (`pkg.installed`, `pkgrepo.managed`, `file.managed`, `file.append`,
  `cmd.run`, `sysctl.present`) instead of Puppet resources. MVP scope only:
  `apt` (plain + `apt_repository` + `add_apt_repo` variants), `sysctl`,
  `file`, `append`, `script`, and a `salt_formula` no-op branch (see below).
  Every other existing step type (`pyenv`/`rbenv`/`cpan`/`asdf`/`choco`/
  `powershell_*`/etc.) is explicitly out of scope for this pass - documented
  in the file's own header as "add a new `{% elif %}` branch here following
  this same pattern" rather than silently unsupported.
- `init.sls` + one file per area (`gen_scripts.sls`, `shell_scripts.sls`,
  `compiled_lang.sls`, `win_scripts.sls`) - hand-written boilerplate (never
  generated), each importing the macro and looping over its own slice of
  `lessons.areas`/`lessons.common_steps`, gated by `lessons.gates.<area>`.
  A `salt_formula`-typed step's `name` gets collected into a top-level
  `include:` list per file (Salt requires `include:` as a top-level
  directive, not something emittable mid-loop from inside the macro) -
  this is how a vendored formula actually gets pulled in.

### 2. `static/` tree - masterless

- `configbox/salt/static/minion` - `file_client: local`, `file_roots.base`
  listing the shared state tree + vendored-formula dir, `pillar_roots.base`
  pointing at `roots/pillar`.
- `configbox/salt/static/roots/pillar/top.sls` (hand-written, targets
  `ubuntu22` to `lessons.common` + `lessons.ubuntu22`) +
  `roots/pillar/lessons/common.sls` (hand-written knob: `lessons: {user:
  vagrant}`) + `roots/pillar/lessons/ubuntu22.sls` (**generated**).
- `configbox/salt/static/roots/salt/top.sls` (hand-written: `base: {ubuntu22:
  [lessons]}`).
- `configbox/salt/scripts/ubuntu22_salt_bootstrap.sh` - idempotent
  (`test -x /usr/bin/salt-call && exit 0`), installs via
  `bootstrap.saltproject.io -X` (install-only, no running minion service
  needed for masterless mode).
- `configbox/salt/static/systems/ubuntu22/Vagrantfile` - boots the box,
  syncs `roots/salt` → `/srv/salt`, `../shared_states` → `/srv/salt-shared`,
  `../.formula-vendor` → `/srv/salt-formulas`, `roots/pillar` → `/srv/pillar`;
  runs the bootstrap script, then `config.vm.provision "apply", type:
  "salt"` with `masterless = true`, `minion_config` pointing at `../minion`.

### 3. `roster/` tree - salt-ssh, self-targeting inside the guest

- `configbox/salt/roster/master` - salt-ssh's own config-dir file, using
  **guest-absolute paths** under `/var/script-tut/configbox/salt/...` (same
  convention Puppet's `enc` Vagrantfile already uses for guest-side
  references), since the actual `salt-ssh` invocation runs inside the guest
  now, not from the host.
- `configbox/salt/roster/roots/pillar/top.sls` - deliberately an empty stub
  (`base: {}`) with a comment explaining this tree's data rides entirely on
  `minion_opts.grains` in the roster file instead; exists only because
  salt-ssh's config expects a resolvable pillar_roots/top.sls.
- `configbox/salt/roster/roots/salt/top.sls` - same as static's (hand-written,
  `base: {ubuntu22: [lessons]}`).
- `configbox/salt/roster/roster.yaml` - **generated**, connection info fixed
  to `host: 127.0.0.1`, `port: 22`, `user: vagrant`, `priv:
  /home/vagrant/.ssh/salt_ssh_id` (a conventional, predictable guest-local
  path - not tied to Vagrant's own per-box key, which was the earlier,
  now-avoided fragility), plus `minion_opts.grains.lessons` carrying the full
  step-data payload in the same shape `static/`'s pillar file uses.
- `configbox/salt/scripts/ubuntu22_salt_ssh_bootstrap.sh` - idempotent:
  installs `salt-ssh` + Python inside the guest; generates a local ed25519
  keypair at `~/.ssh/salt_ssh_id` if absent and appends its public half to
  `~/.ssh/authorized_keys` if not already present (so the guest can SSH into
  itself).
- `configbox/salt/roster/systems/ubuntu22/Vagrantfile` - boots the box, runs
  the ssh-bootstrap script, then a plain `config.vm.provision "shell"` step
  that runs `salt-ssh -c /var/script-tut/configbox/salt/roster
  --roster-file=/var/script-tut/configbox/salt/roster/roster.yaml ubuntu22
  state.apply` - a normal shell provisioner, nothing host-side, no trigger.
- Workflow note for the README: regenerate `roster.yaml` (via
  `generate_salt.rb`, from the host, same as Puppet's manual
  `ruby scriptbox/scripts/generate_puppet.rb ...` step) *before*
  `vagrant provision`, exactly like the existing Puppet trees already work -
  not auto-chained into the Vagrantfile.

### 4. Generator - `scriptbox/scripts/generate_salt.rb`

Mirrors `generate_puppet.rb`'s structure exactly, reusing
`resolve_order.rb` + `generate_chef_databag.rb`'s shared helpers
(`root_key`, `step_to_entry`, `consolidate_apt`, `LESSON_AREAS`,
`COMMON_AREA`, `flatten`, `resolve_included`, `topological_order`,
`check_version_needs!`, `deep_stringify_keys`).

- `TREES = %w[static roster].freeze`, CLI: `<config.yml> <out_path> --tree
  static|roster [--select TAG,TAG] [--exclude TAG,TAG]`.
- One shared `lessons_shape(lessons_data)` helper building the
  `user`/`common_steps`/`gates`/`areas` dict both writers use, so the two
  trees never drift into two different data shapes for the same tree.
- `write_static` dumps `{'lessons' => lessons_shape(...)}` (merged with any
  hoisted `formula_pillar` data) as plain YAML pillar content.
- `write_roster` wraps the same shape under `minion_opts.grains.lessons` in
  the roster's per-host entry, with the fixed `127.0.0.1`/`vagrant`/
  `/home/vagrant/.ssh/salt_ssh_id` connection fields described above.
- **Both writers must use `File.write(path, content, mode: 'wb')`** - same
  reason `generate_puppet.rb` needed it: this dev box's Ruby
  (`x64-mingw-ucrt`) silently corrupts multi-line `cmd` bodies with `\r\n`
  in text mode otherwise.
- `resolve_order.rb`: add `'salt_formula'` to `PACKAGE_TYPES` (one-line,
  additive - `flatten`/`tag_eligible?`/`topological_order` already handle
  any type generically).
- `generate_chef_databag.rb`'s `step_to_entry`: pass through
  `entry[:formula_pillar] = step[:formula_pillar] if step[:formula_pillar]`
  - a harmless additive pass-through shared by the Chef/Ansible/Puppet
  generators too, only ever populated for a `salt_formula`-tagged step none
  of them select by default.

### 5. Vendoring `golang-formula`

- `.gitignore`: new block mirroring `.forge-vendor`'s exactly -
  `configbox/salt/.formula-vendor/*` + `!configbox/salt/.formula-vendor/.gitkeep`.
- Vendor target: `configbox/salt/.formula-vendor/golang/` (the formula
  repo's own `golang/` subtree - its `init.sls`/`map.jinja`/etc.), added as
  a `file_roots` entry in both `static/minion` and `roster/master`.
- New opt-in alternative for the `go` step in `scriptbox/config/ubuntu2204.yml`,
  reusing the **existing** tags/`--select` mechanism (same pattern already
  used for rbenv/pyenv/asdf alternatives - no new selection logic needed):
  the current `apt_repository: ppa:longsleep/golang-backports` entry gets
  `tags: [default]`, and a new sibling entry `salt_formula: golang` +
  `formula_pillar: {golang: {version: '<confirm current stable at build
  time>', pkg: {use_upstream_repo: false}}}` gets `tags:
  [salt_formula_golang]`. Selected via `--select salt_formula_golang`; every
  other generator's default output is unaffected since it never asks for
  that tag.
- `configbox/salt/README.md`: append a "Configbox Configuration Items"
  section (mirrors `puppet/README.md`'s, in Salt's own vocabulary only -
  file_roots/pillar_roots/grains/minion_opts, no other-tool names) and a
  "Vendoring Formulas" section (manual `git clone`/tarball fetch into
  `.formula-vendor`, mirroring the Forge section's spirit).

## Verification

1. `ruby scriptbox/scripts/generate_salt.rb scriptbox/config/ubuntu2204.yml configbox/salt/static/roots/pillar/lessons/ubuntu22.sls --tree static`
   and confirm the output YAML has no `\r` bytes (same check used for the
   Puppet generator: `grep -c $'\r'` / a quick Python byte-count).
2. `vagrant up` in `configbox/salt/static/systems/ubuntu22/`, then
   `vagrant provision` - expect a clean `salt-call --local state.apply`
   exit 0 on a fresh box, and idempotent (no changes) on a second run.
3. `ruby scriptbox/scripts/generate_salt.rb ... --tree roster` then
   `vagrant up` in `configbox/salt/roster/systems/ubuntu22/` - confirm the
   ssh-bootstrap step creates the local keypair once (idempotent on
   re-provision) and `salt-ssh ... state.apply` succeeds targeting
   `127.0.0.1` from inside the guest.
4. Re-run step 2/3's generator + apply with `--select salt_formula_golang`
   and confirm `include: - golang` actually resolves and installs Go via
   the vendored formula instead of the PPA path.
5. Expect real iteration here, same as the Puppet build: first passes at
   Jinja/state syntax (e.g. `pkgrepo.managed`'s exact `key_url`/`aptkey`
   parameter names, the precise unsupported-type fallback state) are
   informed guesses pending a live `state.apply` run, not verified syntax -
   treat the first `vagrant provision` on each tree as the real test, not a
   formality.
